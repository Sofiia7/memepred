### Исходники верифицированы на обозревателе (11.09)

Контракты стека и стенд-ины верифицированы на `explorer.testnet.chain.robinhood.com`, исходный
код открыт. Рынки-клоны обозреватель показывает как прокси EIP-1167 на `PoolOrderbookMarket`, так
что по ссылке на любой рынок виден код. Решение открыть исходники контрактов - Софии, репозиторий
при этом по-прежнему закрыт.

Два стенд-ина - байт-в-байт копии уже верифицированных: второй `MockWETH` (`0x89ea…`, «токен»
первого пула) и пул PEPE (`0xEFd4…`). forge считает их верифицированными («already verified»),
а API обозревателя отмечает `is_verified = false`.

Как повторить - например, на мейннете:

- верифицировать **из того коммита, из которого деплоили**. Он записан в
  `broadcast/<скрипт>/<chainId>/run-latest.json`, поле `commit`; здесь это `344694f` для стека и
  стенд-инов (исходник хранилища менялся 06.09, из `HEAD` он бы не совпал) и текущий для
  `MockToken`, чей файл закоммичен позже. Удобно через отдельное рабочее дерево git;
- `foundry.toml` ссылается на `${BASESCAN_API_KEY}`, и forge требует эту переменную при любой
  верификации, даже для Blockscout. Хватает заглушки `BASESCAN_API_KEY=unused`;
- `forge verify-contract <адрес> <путь:Контракт> --chain-id 46630 --verifier blockscout
  --verifier-url https://explorer.testnet.chain.robinhood.com/api/ --constructor-args <abi> --watch`;
- обозреватель иногда отвечает `Fail - Unable to verify` на верный исходник: здесь так было три
  раза из четырнадцати, и все три прошли простым повтором без правок. Сначала повторить, потом
  искать ошибку.

### Пул ликвидности: включён 2026-09-05 22:19 UTC

Девять часов соука и сорок четыре матча прошли с `is_lp_match = false` во всех до
единого. Причина не в выборке: `LiquidityPool.tryMatch` отвечает нулём, пока
`totalAssets()` равен нулю, поэтому второй слой `_tryMatch` - вся сторона пула -
не исполнялся на этой цепочке ни разу. Ошибки при этом нет, ордер просто ложится
в стакан, и девять часов зелёных цифр прошли мимо.

Внесено 2 WETH через `PHASE=lp`. Размер выбран малым намеренно: контракт
ограничивает экспозицию 10% от `totalAssets` глобально и 5% на рынок, то есть 0.2
WETH открытой позиции по протоколу и 0.1 на один рынок - сорок и двадцать ставок
по `MIN_BET`. Достаточно, чтобы путь работал регулярно, и мало, чтобы пул не стал
контрагентом каждого бота и не превратил соук в другой эксперимент.

Через полчаса после депозита: 46 матчей, из них 2 против пула, дрейф инварианта
по-прежнему ровно `0.000000000000000000`. Учёт LP на этой цепочке сходится.

Попутно: `MIN_DEPOSIT = 50e6` записан как 50 USDC. На 18-значной цепочке это
0.00000000005 WETH, то есть порога минимального депозита здесь нет. Открытой
дверью это не является - атака на первого вкладчика закрыта `_decimalsOffset() = 6`,
который от цепочки не зависит. Это константа, переставшая что-либо значить, и знать
об этом надо до того, как на неё понадеются.

### Второй пул: PEPE, для проверки аварийного возврата

| | Адрес |
|---|---|
| Пул (PEPE/WETH, 1%) | `0xEFd4618F36268CE8c1c8Ad3783bdCa6185221dBd` |
| Токен `PEPE` | `0xC12B7F3F9667c69075a89d3151153CE8E1EE6B4B` |

Заведён `AddRhcPool.s.sol` двумя задачами сразу. Первая - **токен с именем**: в первом
комплекте по обе стороны пула стоял `MockWETH`, и всё читалось как «WETH / WETH».
`poolWatcher` подхватил его сам и создал три рынка, второй раз подряд без рук.

Вторая - **единственный путь возврата денег, который ни разу не выполнялся ни на одной
цепочке**. `emergencyRefundMatch` требует `block.timestamp > settleAt + SETTLE_GRACE`, а
`SETTLE_GRACE` - константа в 24 часа. Соук до этого не доходит: он рассчитывает всё, что
открывает. Поэтому на 60-секундном рынке этого пула создан матч, после чего ликвидность
пула выставлена в ноль.

Состояние на 2026-09-05 21:29 UTC (проверено на цепочке):

| | |
|---|---|
| рынок | `0xC95ab0199FF7AA04CB6D9A385679f9CF9B6671b0` (60 с) |
| матч | 0.005 WETH с каждой стороны, не рассчитан |
| ликвидность пула | 0 |
| резолвер | отказывается давать цену |
| кипер | видит матч готовым и не может закрыть |
| `emergencyRefundMatch` | доступен с **2026-09-06 21:27:30 UTC** |

Забрать: `MARKET=0xC95ab0199FF7AA04CB6D9A385679f9CF9B6671b0 PHASE=refund npx tsx
scripts/rhc-live-cycle.mts` из `backend/`.

Чего кипер при этом **не** делает - не эмитит `MatchUnpriceable` на цепочке. Он сперва
симулирует и, если рассчитать нечего, транзакцию не отправляет, чтобы не сжечь газовый
потолок впустую. Событие остаётся в симуляции, а в логе видно: `1 ready match(es) at
offset 0 cannot settle yet - stepping past them`.
