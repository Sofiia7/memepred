# FlipTheMeme / MemePred: аудит Robinhood Chain

Дата: **28 сентября 2026**. Ветка `robinhood-chain`, исходный HEAD `b1a5326`.

**Вердикт:** технический прототип уже существенный: есть контракты, индексатор, keeper, LP, интерфейс и тестовая история транзакций. Однако текущую связку нельзя считать готовым публичным демо: обнаружены ошибки учёта, восстановления средств и отображения результата; RHC API не доступен по публичному DNS; опубликованные тестовые контракты отстают от исходников. До запуска с реальными средствами остаются отдельные экономические и oracle-риски.

Это аудит с воспроизводимыми проверками, а не исправление продукта. Production-код, конфигурация, деплой и кошельки не изменялись. Добавлены этот отчёт, два Solidity-примера, SQL-пример и скриншоты. Существовавшее изменение вложенного `contracts/lib/openzeppelin-contracts` сохранено.

## 4. Исправления первой очереди

Приоритет **P1**: ошибка денег/учёта/доступности либо блокер достоверного демо. **P2**: заметно ухудшает надёжность и пользовательский сценарий. Приоритет не означает, что каждый пункт — эксплойт контракта.

### A01 · P1 · Ничья закрывает посторонние ожидающие заявки

**Воспроизведено.** [indexer.ts:599](C:/Server/memepred/backend/src/keeper/indexer.ts:599).

Обработчик `MatchTied` обновляет все PENDING/MATCHED orders рынка, у которых не найден незавершённый match. Он не ограничивается order IDs конкретной ничьей. Для заявки, у которой вообще нет matches, `NOT EXISTS` тоже истинен.

Пример: заявки №1 и №3 связаны с завершившимся match, №2 просто ждёт контрагента. SQL переводит **все три** в SETTLED. Контракт №2 остаётся PENDING. `reconcilePayouts` требует наличие settled match и не исправит никогда не исполнявшуюся №2. Автовозврат, который выбирает PENDING/MATCHED, может перестать её видеть.

**Исправить:** ограничить обновление участниками события и вычислять статус по заполнению заявки, возврату остатка и всем её matches. **Проверка:** чужая pending-заявка не меняется; частичная заявка с открытым хвостом остаётся открытой; обычный live indexing и полный backfill дают одинаковую БД.

Пример: [audit-2026-09-28-repro.mjs](C:/Server/memepred/docs/rhc/audit-2026-09-28-repro.mjs).

### A02 · P1 · Событие помечается обработанным до сохранения результата

**По коду.** [indexer.ts:90](C:/Server/memepred/backend/src/keeper/indexer.ts:90), вызовы начиная с 235/454/468.

`markIngested()` отдельно записывает `(tx_hash, log_index)` до чтения block timestamp и последующих SQL-записей. Если RPC/SQL падает после этой вставки, повторный запуск пропускает событие. Даже неизменённый checkpoint не спасает: dedup уже считает событие обработанным. Несколько связанных SQL-записей также могут сохраниться частично.

**Исправить:** RPC-данные подготовить заранее; dedup и все бизнес-записи события выполнять одной транзакцией через один DB client. Checkpoint продвигать только после commit. Обрабатывать порядок логов и отсутствующие зависимости явно.

**Проверка:** принудительное падение после каждой записи + повторное проигрывание; итог совпадает с непрерывным запуском. Добавить backfill, где OrderPlaced/OrderMatched/MatchTied попали в один batch: текущий `tiedOrderKeys` вычисляется до обработки новых matched-событий.

### A03 · P1 · Emergency refund не закрывает match в БД и может остановить дальнейшие автовозвраты

**По коду.** [OrderbookMarket.sol:729](C:/Server/memepred/contracts/src/OrderbookMarket.sol:729), [indexer.ts:566](C:/Server/memepred/backend/src/keeper/indexer.ts:566), [resolveKeeper.ts:376](C:/Server/memepred/backend/src/keeper/resolveKeeper.ts:376).

Контракт ставит `match.settled=true`, но emits только `OrderRefunded`, без события с match ID. Индексатор обновляет заявку, а не терминальное состояние match. Keeper берёт старейшие `settled=false`, ограничивая выборку 20; успешный refund только логируется. Повторная симуляция уже возвращённого match отклоняется, и запись снова остаётся в выборке.

После накопления 20 таких записей более новые просроченные matches могут никогда не попадать в обработку. Убирание старых строк из health view не устраняет причину.

**Исправить:** отдельное `MatchRefunded(matchId, reason)` для нового деплоя; reconciliation on-chain terminal state для старого; хранить суммы/виды возвратов. После подтверждённого refund обновлять/сверять БД, а не только писать лог.

**Проверка:** 25 просроченных matches, первые 20 уже возвращены; оставшиеся 5 обрабатываются. Повторный replay идемпотентен. Сумма возвратов сверяется с токеновыми переводами.

### A04 · P1 · UI скрывает выигрыш у заявки с несколькими исходами

**Контрактная часть воспроизведена; UI-ветка подтверждена кодом.** [useOrderStatus.ts:30](C:/Server/memepred/frontend/src/hooks/useOrderStatus.ts:30), [OrderStatusCard.tsx:171](C:/Server/memepred/frontend/src/components/OrderStatusCard.tsx:171), [Portfolio.tsx:88](C:/Server/memepred/frontend/src/pages/Portfolio.tsx:88).

UI сводит заявку к её **первому** match. Из-за этого:

- Первый match tied, последующий won: ранний return «ничья» скрывает выигрыш и Claim.
- Первый match уже завершён, второй завис: Recover нацелен на первый match ID.
- Один match выигран, другой emergency-refunded: контрактный status становится REFUNDED, но накопленный payout остаётся доступным через `claim()`. OrderStatusCard и Portfolio не предлагают этот claim.

В audit case ставка Alice 0.02 WETH исполнилась двумя частями по 0.01. Первая выиграла, вторая вернулась через emergency refund. У заявки status REFUNDED, но Alice успешно забрала **ещё 0.02 WETH** через `claim`. В тестовом конструкторе fee=0; сам дефект жизненного цикла от комиссии не зависит.

**Исправить:** модель заявки должна агрегировать все исполнения: active stake, returned principal, realised result, claimable amount, pending matches. Доступность Claim выводить из условий контракта, а не одного enum. Возвращать каждый просроченный match отдельно/пакетом.

**Проверка:** win+tie, tie+win, win+loss, win+emergency, несколько emergency, частичный fill+возврат хвоста. Проверить после reload, а не только при получении live events.

### A05 · P1 · Ошибка проверки адреса рынка разрешает переход к approve

**По коду; вредоносные транзакции не выполнялись.** [Market.tsx:50](C:/Server/memepred/frontend/src/pages/Market.tsx:50), [usePlaceBet.ts:211](C:/Server/memepred/frontend/src/hooks/usePlaceBet.ts:211).

`notAMarket = isRealMarket === false`. При RPC error значение остаётся undefined, loading заканчивается, Composer становится доступным. Shared hook не проверяет `factory.isMarket` самостоятельно и может запросить token approval до проверки доступности `marketFeedId`. Ссылка на произвольный адрес плюс отказ проверки открывают путь к approval непроверенному spender. Approval ограничен суммой ставки, но это всё равно деньги пользователя.

**Исправить:** разрешать торговлю только при положительном `isMarket === true`; в общем execute-пути повторно проверять адрес, factory, chain/account до любой подписи. Показывать отдельное «не удалось проверить рынок» с Retry. Главная страница также должна использовать этот preflight.

**Проверка:** false, revert, timeout, undefined, invalid address, chain change — ни один случай не вызывает approve/place. Валидный подтверждённый рынок проходит.

### A07 · P1 для достоверных результатов · RHC не записывает ценовую историю для UI

**По коду.** [keeper/index.ts:98](C:/Server/memepred/backend/src/keeper/index.ts:98), [priceRecorder.ts](C:/Server/memepred/backend/src/keeper/priceRecorder.ts), [markets.ts](C:/Server/memepred/backend/src/routes/markets.ts), [Markets.tsx:106](C:/Server/memepred/frontend/src/pages/Markets.tsx:106).

`recordAllPrices` стартует только при `pushesPricesOnChain`, у RHC это false. При этом candles/stats продолжают читать `price_history`; существующий recorder рассчитан на Base symbols/USD. Factory indexing не создаёт альтернативную историю цен. На свежей RHC БД графики и карточки остаются без необходимых данных. Чтение текущего TWAP на отдельной странице не заполняет историю.

**Исправить:** отдельный off-chain RHC collector без лишних on-chain транзакций; ключ `(chainId, poolAddress)`, единица token/WETH, timestamp/freshness, spot и TWAP с понятной подписью. Не включать старый Base recorder без адаптации. Символ не годится как уникальный идентификатор пула.

**Проверка:** чистая БД → реальные ценовые точки → candles/card/chart; два пула с одинаковым symbol не смешиваются; сбой RPC не превращается в цену 0 или «LIVE».

### A08 · P1/P2 · Очередь settlement может застревать за непрайсируемой головой

**По коду, нагрузочный пример не запускался.** [resolveKeeper.ts:199](C:/Server/memepred/backend/src/keeper/resolveKeeper.ts:199), строки 218/306/345.

Offset начинается с нуля на каждом tick и сбрасывается после успешного батча. При стандартных 8 циклах по 25 позиций одна непрайсируемая запись удерживает голову, а обработанные/пропущенные записи остаются за ней. Когда до новых ready matches накопится достаточно позиций, следующие ticks снова проходят один и тот же префикс. Новые matches могут ждать до снятия блокирующей головы, в том числе до 24-часового refund.

**Исправить:** устойчивое продвижение по очереди с учётом изменения head; отдельный bounded retry для unpriceable matches; не начинать полный обход с нуля каждый tick.

**Проверка:** 250+ matches, первый навсегда unpriceable, остальные валидны. Последние должны обрабатываться за ограниченное число ticks без ожидания 24 часов.

## 5. Логика ставок, oracle и экономика

### L01 · Ожидающая заявка не сохраняет ценовой предел

**Воспроизведено.** [OrderbookMarket.sol:388](C:/Server/memepred/contracts/src/OrderbookMarket.sol:388), [OrderbookMarket.sol:462](C:/Server/memepred/contracts/src/OrderbookMarket.sol:462).

`expectedPrice/slippageBps` проверяются только при подаче. В Order этот предел не сохраняется; поздний taker исполняет старую заявку по новой текущей цене. Audit case: Alice отправила заявку с ценой 1 и допуском 1%; через 120 секунд, внутри 5-минутного matching window, она сматчилась по **2.000036323830947322**.

Это не обход проверки в самой транзакции taker: это отсутствие защиты цены на весь срок ожидающей заявки. Entry TWAP/spot guard тоже не помогает, если новая цена уже стабилизировалась.

Нужно выбрать и реализовать спецификацию: либо сохранять допустимый диапазон maker и пропускать/отменять вышедшие из него заявки, либо прямо продавать «ставку относительно цены будущего исполнения», показывая плавающий strike, дедлайн и возможность отмены. Для real-money launch оставлять текущую двусмысленность нельзя. Один order также может получить разные strikes и deadlines для разных fills — это должно быть видно в UI.

### L02 · «Подождём, пока цена успокоится» не соответствует exit oracle

[PoolOracleResolver.sol:288](C:/Server/memepred/contracts/src/PoolOracleResolver.sol:288), [RiskDisclosure.tsx](C:/Server/memepred/frontend/src/components/RiskDisclosure.tsx).

Exit TWAP и сравниваемое короткое окно привязаны к историческому `settleAt`. Если spread между ними превысил лимит, повторный вызов позже читает тот же исторический период. Возвращение текущей цены к норме не исправляет это окно. Текст RiskGate обещает обратное. `MarketRefunded` в resolver при этом не означает фактическую отправку возврата.

Нужны явные `awaiting settlement / unpriceable / refund available`, точное время разблокировки и согласованная политика для необратимо непрайсируемого окна. Измерить на реальных пулах долю обычных движений, ведущих к 24-часовой блокировке. Не обещать пользователю гарантированный результат ровно через 1/5/15 минут.

### L03 · Начальный depth gate не ограничивает дальнейший oracle-риск

[PoolMarketFactory.sol:241](C:/Server/memepred/contracts/src/PoolMarketFactory.sol:241), [PoolOracleResolver.sol:162](C:/Server/memepred/contracts/src/PoolOracleResolver.sol:162).

2 WETH virtual-depth проверяются при создании. Позже resolver требует liquidity > 0, а не сохранения глубины. Virtual reserve также не равен измеренной стоимости манипуляции на всех ценовых диапазонах. Открытый риск контракта/LP не привязан к текущей стоимости сдвига TWAP. Лимит 0.04 WETH на заявку не ограничивает множество заявок/адресов.

Перед real-money нужны текущая оценка ликвидности/концентрации, cap суммарного открытого риска по pool/feed, мониторинг и остановка новых ставок при деградации. Отдельно проверить прибыльность атак на TWAP lag даже в пределах разрешённого 2% spread. Это экономический риск; выполненного прибыльного эксплойта в этом аудите нет.

### L04 · Treasury получает недостаточно для части LP-матчей даже по старой модели газа

[OrderbookMarket.sol:627](C:/Server/memepred/contracts/src/OrderbookMarket.sol:627), [OrderbookMarket.sol:667](C:/Server/memepred/contracts/src/OrderbookMarket.sol:667), [RhcFeeDistributor.sol:31](C:/Server/memepred/contracts/src/RhcFeeDistributor.sol:31).

Protocol fee взимается в ветке выигрыша пользователя. Если выигрывает LP, банк возвращается LP без protocol fee. Распределение 90% treasury / 10% referral применяется только к полученной комиссии.

Иллюстрация на **исторических**, не сегодняшних данных из [measurements](C:/Server/memepred/docs/rhc/measurements/README.md): ставка 0.005 WETH, банк 0.01, protocol fee 1%, referrer присутствует.

| Сценарий | Treasury на match |
|---|---:|
| PvP, есть победитель | 0.00009 WETH |
| LP, пользователь выиграл | 0.00009 WETH |
| LP, пользователь проиграл | 0 |
| LP при условных 50% пользовательских побед | в среднем 0.000045 WETH |
| Tie / refund | 0 |
| Историческая оценка marginal gas: 162029 × 0.398 gwei | 0.00006449 ETH |

Даже без referral LP-ожидание 0.00005 ниже этой газовой оценки. Это вывод о **покрытии расходов treasury**, не доказательство отрицательного суммарного PnL LP+treasury. В расчёт ещё не включены fixed gas, retries, refunds, RPC, хостинг. Keeper помечает settlement critical, поэтому тезис старых документов «переждём дорогой газ» нельзя переносить на фактическое поведение.

Нужно измерить PvP/LP/win/loss/tie/refund отдельно на финальном коде и обновлённом gas sample; определить резерв/субсидию и пополнение ETH keeper из WETH treasury. Если прибыль LP должна оплачивать keeper, это должно быть явным механизмом, а не предположением.

### L05 · Смена factory multisig не меняет authority уже созданных рынков

[PoolMarketFactory.sol:203](C:/Server/memepred/contracts/src/PoolMarketFactory.sol:203), [PoolMarketFactory.sol:369](C:/Server/memepred/contracts/src/PoolMarketFactory.sol:369), [OrderbookMarket.sol](C:/Server/memepred/contracts/src/OrderbookMarket.sol).

Рынки сохраняют multisig при initialize. `setMultisig` меняет factory/future markets; старые рынки продолжают использовать прежний адрес для unpause. `unpauseFeed` снимает feed-флаг, но не заменяет локальную authority/paused state старого рынка.

В [DeployRhc.s.sol:90](C:/Server/memepred/contracts/script/DeployRhc.s.sol:90) проверяются ненулевой multisig и его отличие от deployer, но это не проверка того, что адрес действительно является настроенным Safe: другой EOA также проходит.

Перед mainnet: проверенный управляющий Safe, отдельные production keys, определённый путь ротации всех ролей и проверка pause→rotate→unpause на существующем рынке. EOA на testnet сам по себе не является блокером хакатонного демо.
